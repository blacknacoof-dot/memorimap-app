Memorimap 구조 요약 + 기능 검증 시나리오 마스터 문서
기준일: 2026-03-20

1. 전체 구조 요약

- 앱은 React + Vite 기반 SPA이며, 실제 조립 중심은 App.tsx다.
- 화면 결정은 URL만으로 이뤄지지 않고, internal viewState + HashRouter + 일부 query param이 함께 작동하는 하이브리드 구조다.
- 일반 사용자 화면은 대부분 viewState가 최종 source of truth이고, 관리자 계열 일부만 URL에 안정적으로 고정된다.
- 데이터 접근은 lib/queries.ts, lib/api/*.ts, hooks/*.ts, services/*, supabase/functions/*에 분산되어 있다.
- 동일 의미의 값이 여러 표현으로 존재한다. 대표적으로 plan_id / plan_name / subscription_plans.id, facility_id / facility_id_uuid / facility_id_bigint가 있다.
- 핵심 도메인은 유저 탐색, 예약, AI 상담, 비교, 마이페이지, 시설 관리자, 상조 관리자, 슈퍼 관리자, 구독/결제, 승인/리포트다.

2. 엔트리 / 라우팅 / 화면 결정 구조

- 진입점: index.tsx
- 앱 조립 중심: App.tsx
- URL 해석: lib/appRouteConfig.ts, components/RouteStateSync.tsx
- 렌더링 분기: components/AppRouteLayout.tsx, components/ContentRouter.tsx
- 슈퍼 관리자 탭 source of truth: components/SuperAdmin/SuperAdminDashboard.tsx의 ?tab= query param

라우팅 특징
- /admin, /facility-admin, /super-admin, /funeral-company, /partner-inquiry는 route-driven view다.
- MAP, LIST, MY_PAGE, CONSULTATION, SANGJO_DASHBOARD, SUBSCRIPTION_PLANS, PERSONAL_SUBSCRIPTION 등은 대부분 internal state-driven view다.
- /auth는 로그인 모달을 여는 진입점이다.
- /share/:token은 share layout이다.
- /external-browser-guide는 별도 안내 페이지다.

5. 데이터 접근 구조

- 직접 Supabase 호출, queries 계층, api 계층, services 계층, Edge Function 호출이 병렬 존재한다.
- lib/queries.ts는 단순 query layer가 아니라 업무 흐름 계층이다.
- 일부 기능은 RPC 중심이고, 일부는 테이블 직접 접근이다.
- 즐겨찾기, AI, 승인, 구독은 각기 다른 경로가 섞여 있다.
- 계약 불일치 가능성이 큰 지점은 facility_subscriptions, favorites, ai_consultations, reservations이다.

6. 상태 관리 구조

- App.tsx local state가 가장 크다.
- viewState가 일반 화면 렌더링의 핵심 상태다.
- useFilterStore는 검색 / 카테고리 / 정렬 상태를 갖는다.
- useChatStore는 글로벌 AI 오픈 상태만 갖는다.
- useComparison은 시설 비교 / 상조 비교 로컬 state를 갖는다.
- React Query는 운영성 데이터와 RPC 결과에서 주로 사용된다.

8. 실패 / 정합성 / 권한 우회 / 상태 충돌 보강

8-1. 실패 시나리오 레이어

- [P0-FAIL] 예약 생성 실패
  - 조건: 비로그인, facility_id null, quota 초과, 결제 실패
  - 확인: insert 미발생, 에러 UI 표시, MyPage 이동 없음

- [P0-FAIL] 구독 변경 실패
  - 조건: 권한 없음, auth client 실패, plan_id 비정상 값
  - 확인: DB 미변경, UI 실패 표시, 기존 플랜 유지

- [P0-FAIL] AI 상담 실패
  - 조건: quota 초과, gemini proxy 실패, consultation create 실패
  - 확인: 상담 저장 안 됨, 에러 메시지 노출, 반쪽 데이터 없음

- [P0-FAIL] 승인 실패
  - 조건: 일반 유저 승인 시도, Edge Function 호출 실패, RPC 실패
  - 확인: 승인 상태 미변경, 에러 응답 표시

8-2. 데이터 정합성 검증 시나리오

- [P0-DATA] 구독 plan_id 정합성
  - 단계: 무료 -> 유료 -> 무료 전환
  - 확인: facility_subscriptions.plan_id, subscription_plans.id, UI 표시값
  - 기대: canonical id 동일, plan_name mismatch 없음

- [P0-DATA] facility_id 계약 검증
  - 확인: reservations.facility_id, facility_subscriptions.facility_id_uuid, join 정상 여부
  - 기대: 고아 데이터 없음, 관리자 조회 정상

- [P0-DATA] 상조 계약 정합성
  - 확인: sangjo_contracts.sangjo_id, PartnerDashboard 상담/계약 병합 결과
  - 기대: 계약이 상담 목록에 중복/누락 없이 반영

- [P0-DATA] 즐겨찾기 정합성
  - 확인: favorites / sangjo_favorites / user_favorites 경로별 반영
  - 기대: 추가/삭제 후 조회값 일치

8-3. 권한 우회 시나리오

- [P0-SEC] 시설 관리자 권한 우회
  - 시도: 비로그인 상태에서 /facility-admin 직접 진입, 일반 유저로 직접 진입
  - 확인: redirect 또는 block, API 호출 차단
  - 기대: 데이터 노출 없음

- [P0-SEC] 상조 관리자 권한 우회
  - 시도: 일반 유저로 /super-admin, /facility-admin, /sangjo-dashboard 진입
  - 확인: 차단 문구 또는 강제 이동
  - 기대: 관리자 데이터 미노출

- [P0-SEC] 예약 승인 API 직접 호출
  - 시도: 일반 유저가 approveReservation 또는 rejectReservation 경로 호출
  - 확인: DB 변경 여부
  - 기대: 실패

- [P0-SEC] Edge Function 직접 호출
  - 시도: approve-partner, send-monthly-report 직접 호출
  - 확인: 서비스 롤 / 권한 검증 실패 여부
  - 기대: 비인가 요청 차단

8-4. 상태 / 라우팅 충돌 시나리오

- [P0-STATE] viewState vs URL sync
  - 단계: MAP -> LIST 이동, 뒤로가기, 새로고침
  - 확인: 화면 유지 여부, viewState 재구성, canonicalization
  - 기대: UI 깨짐 없음

- [P0-STATE] 관리자 route-driven state 충돌
  - 단계: /super-admin?tab=monitoring, 다른 탭으로 이동, 뒤로가기
  - 확인: query param이 activeTab으로 유지되는지
  - 기대: 탭 상태 일관성 유지

- [P0-STATE] AI overlay 해제 충돌
  - 단계: global chat open 후 시설 상세 / 예약 / 비교를 동시에 여닫기
  - 확인: aiChatFacility, selectedFacility, showComparison 간 충돌 여부
  - 기대: 오버레이가 꼬이지 않음

9. 실제로 터질 가능성이 높은 버그 Top 5

1. 예약 저장은 성공했는데 MyPage 반영이 누락되는 경우 [해결됨]
   - 원인: insert 성공 후 local state 갱신 실패 또는 이동 타이밍 불일치

2. plan_id mismatch로 구독 UI가 깨지는 경우 [해결됨]
   - 원인: canonical id, plan_name, subscription_plans.id 불일치

3. AI 상담 데이터가 3개 테이블에 분산되어 이력 / 현재 상태가 서로 달라지는 경우 [해결됨]
   - 원인: ChatInterface, ConsultationView, ScenarioBot가 서로 다른 저장 경로 사용

4. 관리자에서 facility 연결이 안 맞는 경우
   - 원인: uuid / bigint / legacy id 혼용

5. quota 실패 시 fail-open으로 제한이 풀리는 경우
   - 원인: RPC 실패를 allowed=true로 처리하는 경로

10. 실전 QA 문서로 올리기 위한 최소 보강 원칙

- 모든 P0 시나리오에 실패 케이스를 최소 1개 포함한다.
- 모든 구독 / 예약 / 상담 시나리오에 데이터 정합성 검증을 포함한다.
- 모든 관리자 기능에 직접 URL 진입과 권한 우회 시도를 포함한다.
- 화면 이동 시나리오에는 뒤로가기, 새로고침, deep link를 포함한다.
- 정상 흐름만 있으면 QA 문서가 아니라 기능 소개 문서에 가깝다.

12. 기능 검증 전에 반드시 알아야 할 핵심 10개

1. 일반 화면은 viewState가 최종 기준이다.
2. route-driven view는 일부 관리자 화면뿐이다.
3. 슈퍼관리자 탭은 query param 기준이다.
4. 예약 저장은 useReservations가 최종 insert를 한다.
5. AI 상담은 최소 3개 계열이 있다.
6. 시설 비교와 상조 비교는 DB 저장이 없다.
7. 구독은 canonical plan_id 기준으로 봐야 한다.
8. facility_id만으로 고아 레코드 여부를 판단하면 안 된다.
9. 승인 / 리포트는 Edge Function과 RPC가 함께 얽혀 있다.
10. 즐겨찾기 / 예약 / 상담 / 구독은 서로 다른 테이블과 invalidation 경로를 가진다.
